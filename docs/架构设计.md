> 文档版本 v2.0 ｜ 2026-08-31
> 上游输入：v1.0 架构（2026-08-29，已产出工程骨架）+ 2026-08-31 定稿的 UI 设计稿（5 屏，Apple 风格）
> 技术栈：原生小程序 + 微信云开发 ｜ 主体：企业/个体工商户 ｜ 题库：自研

## 0. 一页纸结论

| 决策项 | 结论 | 为什么 |
|---|---|---|
| 开发框架 | **原生小程序**（不用 Taro/uni-app） | V1 只发微信一端。跨端框架带来 15~20% 性能损耗与调试成本，换不来收益 |
| 后端 | **微信云开发（标准版及以上）** | 免服务器/域名/SSL/后端备案/登录态，上线周期压缩 2~3 周 |
| 云开发套餐 | **标准版起，不能用个人版** | 个人版云函数超时锁死 3s、内存锁死 256MB，判题事务必然超时 |
| UI 组件库 | **手写组件**，不引 TDesign 全量 | 全量约 300KB+，吃掉主包 2MB 预算的 15%。刷题 UI 简单，自研组件足够 |
| 数据访问 | **全部走云函数**，集合安全规则设为「仅管理端」 | 题库是核心资产，客户端直连可被批量拖库 |
| 判题位置 | **云端判题** | 下发的题目不含 `answer`，从源头杜绝题库泄露 |
| 状态管理 | `globalData` + 自研事件总线 | mobx-miniprogram 约 30KB，V1 规模用不上 |
| 底部 Tab | **首页 / 题库 / 错题本 / 我的** | 模考确认不做，UI 稿的模考位 V1 由错题本占用 |
| 限时模考 | **V1 不做** | 4 周排期下会挤压核心闭环。分包位 `pkg-exam` 预留给 V1.1 |

### 1.2 V1 明确不做（写下来是为了防止范围蔓延）

| 不做 | 原因 | 何时做 |
|---|---|---|
| **限时模考** | 需计时器、自动交卷、模考报告、历史对比，约 1 周工期，会挤压核心闭环联调 | V1.1，`pkg-exam` 已预留 |
| 会员付费 / 虚拟支付 | 微信对商业类目会核验 **ICP 经营许可证**（非备案），要求内资、注册资本 ≥100 万、3 人社保，办理周期以月计 | 有稳定 DAU 后再启动 |
| UGC（题目上传、评论区） | 一旦有 UGC 就必须接 `msgSecCheck` / `imgSecCheck`，且需内容审核人力 | V2 |
| 多端（H5 / App / 支付宝） | 违背「V1 只发一端」的前提 | 视增长情况 |

### 1.3 Tab 方案（本节是本次相对 UI 稿的唯一改动）

UI 稿的 Tab 是 `首页 / 题库 / 模考 / 我的`。因 V1 不做模考，**第 3 个 Tab 改为「错题本」**。

理由：
1. 「题库」Tab 与首页 6 宫格存在入口重叠，若第 3 个 Tab 也闲置，底部导航等于浪费 1/4 的黄金位置
2. 错题本是刷题类工具的第二高频入口，且是「复访 → 重做 → 掌握」留存闭环的载体
3. `tabBar.list[].pagePath` **必须指向主包页面**，错题本列表本身很轻（约 30KB），代价可接受

V1.1 模考上线时，把错题本收进「我的」页，第 3 个 Tab 让位给模考——此时主包结构不变，只是 `app.json` 的 `tabBar.list` 顺序调整。

## 2. 技术选型

### 2.1 为什么是云开发

传统自建后端要跑完这条链：**买服务器 → 买域名 → ICP 备案 → 申请 SSL → 配置 HTTPS → 微信后台配 request 合法域名 → 后端实现登录态**。
云开发把这条链砍到只剩「开通环境」一步。

| 能力 | 云开发方案 |
|---|---|
| 用户鉴权 | `cloud.getWXContext()` 直接拿 openid，无需 `wx.login` + code2session |
| 数据库 | 云数据库（文档型，MongoDB 语法） |
| 文件存储 | 云存储，自带 CDN |
| 定时任务 | 定时触发器（Cron），用于生成每日任务、刷新榜单缓存 |
| 服务端逻辑 | 云函数（Node.js） |

### 2.2 云开发套餐：必须标准版（本次修正）

v1.0 文档只写了「云函数超时可达 900s」，漏了套餐差异。核对 2026 年官方配额后必须纠正：

| 配额 | 个人版 | 标准版 | 企业版 |
|---|---|---|---|
| 云函数超时 | **3s，不支持修改** | 最大 900s | 最大 900s |
| 云函数内存 | **256MB，不支持修改** | 可修改 | 可修改 |
| 环境 QPS | 500 | 500 | 1000 |
| 调用次数 | 20 万次/月 | 800 万次/月 | 5000 万次/月 |
| 数据库容量 | 3 GB/月 | 100 GB/月 | 500 GB/月 |
| 日志保存 | 2 小时 | 3 天 | 7 天 |

> **结论：个人版不可用。** 判题链路包含「查题目 → 写 records → upsert 错题本 → 更新统计」的事务操作，3 秒超时 + 256MB 内存在批量提交场景必然失败。
> **选标准版**。日志只存 3 天，所以**业务关键日志必须写进数据库集合**（见 §6.4 的 `track` 设计），不要只依赖云函数日志排查问题。

### 2.3 依赖与版本基线

```
运行时依赖：零（不装任何 npm 包进主包）
            —— 刻意设计，主包体积全部留给业务代码
开发工具：微信开发者工具（最新稳定版）
最低基础库：2.25.0
```

基础库 2.25.0 的决策依据（覆盖约 98% 微信用户，且满足全部所需能力）：

| 能力 | 所需基础库 |
|---|---|
| Canvas 2D（战报海报） | 2.9.0+ |
| 头像填写 `open-type="chooseAvatar"` | 2.21.0+ |
| 昵称填写 `input type="nickname"` | 2.21.0+ |
| 隐私授权 `wx.getPrivacySetting` | 2.32.3+ |
| 订阅消息 `wx.requestSubscribeMessage` | 2.8.2+ |

> ⚠️ 隐私授权需要 **2.32.3+**。若把最低基础库定在 2.25.0，必须在代码里做**能力检测降级**：
> `if (wx.getPrivacySetting) { ... } else { 跳过隐私授权流程 }`，否则低版本基础库调用会直接报错。

### 2.4 数据库硬限制（设计约束）

| 限制 | 值 | 影响 |
|---|---|---|
| `limit` 小程序端 | 默认 20，**最大 20** | 客户端禁止直连数据库，这条限制对我们无影响 |
| `limit` 云函数端 | 默认 20，**最大 1000** | 分页设计上限，实测单页 20 条体验最好 |
| 单条记录大小 | 1 MB | 题目含大量图片时必须存云存储 fileID，不存 base64 |
| 批量写入 | 建议每批 ≤ 500 条 | 提交 20 题作答完全无压力 |

### 3.2 分包体积预算

微信小程序硬限制（2026 官方）：
- **单个分包/主包 ≤ 2MB**
- **整个小程序所有分包 ≤ 30MB**（服务商代开发的小程序为 20MB）

主包安全线定在 **1.2MB**，给图标和业务迭代留余量。

| 区块 | 预算 | 说明 |
|---|---|---|
| 业务代码（6 页面 + 8 组件 + utils/services） | ~500 KB | 手写，无第三方依赖 |
| tabBar 图标 8 张（81×81 PNG） | ~25 KB | 每张 2~3KB，远低于微信 40KB 单图上限 |
| 其他图片（空状态、默认头像） | ~80 KB | 默认头像 96×96 |
| **主包合计** | **~605 KB** | 距 1.2MB 安全线有充足余量 |
| pkg-rank（打卡/排行/海报） | ~120 KB | Canvas 2D 绘制逻辑 |
| pkg-exam（V1.1） | ~150 KB | 预留 |

### 3.3 预下载规则

```json
"preloadRule": {
  "pages/index/index":  { "network": "all",  "packages": ["pkg-rank"] },
```

首页是最大流量入口，进首页即静默预下载打卡分包，用户点「每日打卡」时零等待。

## 4. 设计令牌与 UI 体系

### 4.1 令牌定义（写入 `styles/tokens.wxss`）

对齐 UI 设计稿的 Apple 风格：

```css
page {
  /* 颜色 */
  --bg-page:        #F5F5F7;   /* 页面底色（羊皮纸白） */
  --bg-card:        #FFFFFF;   /* 卡片底色 */
  --bg-card-dark:   #272729;   /* 深色卡片（今日目标） */
  --text-primary:   #1D1D1F;   /* 主文字（墨色） */
  --text-secondary: #6E6E73;   /* 次级文字 */
  --text-inverse:   #FFFFFF;   /* 深色卡上的文字 */
  --color-primary:  #0066CC;   /* 唯一主色 */
  --color-success:  #34C759;   /* 答对 */
  --color-danger:   #FF3B30;   /* 答错 */
  --border-hair:    #E0E0E0;   /* 发丝线 */

  /* 圆角 */
  --radius-card:  16rpx;
  --radius-capsule: 999rpx;    /* 胶囊按钮 */

  /* 间距（4pt 网格） */
  --space-xs: 8rpx;  --space-sm: 16rpx;
  --space-md: 24rpx; --space-lg: 32rpx; --space-xl: 48rpx;
}
```

### 4.2 字体方案（小程序需要特别处理）

UI 稿指定：中文 Noto Sans SC，数字/计时 Inter。

**小程序不能打包字体文件**（一个中文字体子集动辄 1~3MB，直接吃掉主包预算）。处理方案：

```css
page {
  font-family: -apple-system, BlinkMacSystemFont, "PingFang SC",
               "Helvetica Neue", "Microsoft YaHei", sans-serif;
}
.timer, .stat-number {
  font-variant-numeric: tabular-nums;   /* 等宽数字，防止计时器跳动 */
  font-feature-settings: "tnum";
}
```

- iOS 上 `-apple-system` 即 SF Pro，视觉上非常接近 Noto Sans SC 的观感
- 计时器、正确率等数字用 `tabular-nums` 保证数字等宽，避免秒数变化时宽度抖动
- **不要在小程序里引入 Inter 字体文件**

### 4.3 主色使用约束

`--color-primary` 是**唯一**主色，只允许用在：按钮填充、选中态、进度条、链接。
禁止用主色做大面积背景色块——这是 UI 稿「单一蓝色主色」原则的核心。

| 语义色 | 值 | 用途 |
|---|---|---|
| 答对 | `#34C759` | 解析页正确横幅、选项正确态 |
| 答错 | `#FF3B30` | 解析页错误态、用户选错的选项 |
| 未选中选项 | `--border-hair` | 发丝线描边 |

## 5. 数据模型

云开发数据库是文档型。**所有集合安全规则设为「仅管理端可读写」**，客户端一律通过云函数访问。

### 5.1 集合清单

| 集合 | 用途 | 预估量级（1 万 DAU / 半年） |
|---|---|---|
| `users` | 用户主档、统计、打卡状态 | 30 万 |
| `questions` | 题库（核心资产） | 5 千 ~ 2 万（固定） |
| `qgroups` | 材料题共用材料（资料分析/言语理解） | 1 千 |
| `records` | 答题流水 | 3000 万 ⚠️ 最大集合 |
| `wrong_book` | 错题本（冗余表，避免聚合 records） | 300 万 |
| `favorites` | 收藏 | 50 万 |
| `checkins` | 每日打卡 | 500 万 |
| `daily_task` | 每日任务（预生成题集） | 365 |
| `config` | 运营配置 / 审核开关 | 20 |
| `rank_week` | 周榜缓存（定时刷新） | 1 万 |
| `events` | 埋点流水（`track` 落库） | 200 万/月 |

### 5.2 核心 Schema

**questions** — 题库
```js
{
  qid: 10001,                  // 业务主键，Number，唯一索引
  module: '资料分析',           // 常识判断|言语理解|数量关系|判断推理|资料分析
  subtype: '增长率计算',        // 二级考点
  type: 'single',              // single | multi | material
  stem: '题干文本',
  options: [{ key: 'A', text: '选项内容' }],
  answer: ['B'],               // 数组，兼容多选
  analysis: '解析文本',
  difficulty: 3,               // 1-5
  tags: ['增长率', '基期量'],
  materialId: null,            // type=material 时指向 qgroups.gid
  images: [],                  // 云存储 fileID，绝不存 base64
  source: 'self',              // 自研标记，版权合规用
  status: 1,                   // 1 上架 / 0 下架
  stat: { done: 0, correct: 0 }, // 全局作答统计，用于难度校准
  createdAt: Date
}
```

**users** — 用户主档
```js
{
  _openid: 'oXXXX',            // 唯一索引
  profile: { nickName: '', avatarUrl: '', grade: '省考' },
  inviteBy: null,              // 邀请人 _openid，自建好友关系
  checkin: { streak: 0, maxStreak: 0, lastDate: '', totalDays: 0 },
  stats: {
    totalDone: 0, totalCorrect: 0,
    byModule: {                // 定长 5 键，前端可直接渲染
      '常识判断': { done: 0, correct: 0 },
      '言语理解': { done: 0, correct: 0 },
      '数量关系': { done: 0, correct: 0 },
      '判断推理': { done: 0, correct: 0 },
      '资料分析': { done: 0, correct: 0 }
    }
  },
  subMsg: { checkin: 0 },      // 订阅消息剩余可推送次数
  createdAt: Date, lastActiveAt: Date
}
```

**records** — 答题流水（只增日志）
```js
{ _openid, qid, module, chosen: ['B'], correct: true, costMs: 12000,
  scene: 'practice',   // practice|review|checkin|exam
  date: '2026-08-31',  // 冗余日期，便于按天聚合
  createdAt: Date }
```

**wrong_book** — 错题本
```js
{ _openid, qid, wrongCount: 2, rightStreak: 0, mastered: false,
  lastWrongAt: Date, createdAt: Date }
```
> 移除规则：连续答对 2 次（`rightStreak >= 2`）自动置 `mastered: true`。这是艾宾浩斯记忆曲线的最简实现。

**checkins**
```js
{ _openid, date: '2026-08-31', doneCount: 10, correctCount: 7,
  durationSec: 320, createdAt: Date }
```

**config** — 运营配置（**提审救命用**）
```js
{ key: 'audit_mode',    value: false }    // 审核模式：隐藏分享诱导、排行榜等敏感入口
{ key: 'share_text',    value: '...' }    // 分享文案，可热更
{ key: 'min_version',   value: '1.0.0' }  // 强制更新
{ key: 'home_banner',   value: {...} }
```

### 5.3 索引清单

| `questions` | `subtype + status` | 非唯一 |
| `users` | `_openid` | 唯一 |
| `users` | `stats.totalDone`（倒序） | 非唯一 |
| `records` | `_openid + createdAt`（倒序） | 非唯一 |
| `records` | `_openid + qid` | 非唯一 |
| `wrong_book` | `_openid + mastered + lastWrongAt`（倒序） | 非唯一 |
| `favorites` | `_openid + qid` | **唯一**（防重复收藏） |
| `checkins` | `_openid + date` | **唯一**（防重复打卡） |
| `checkins` | `date + correctCount`（倒序） | 非唯一（排行榜用） |

> 其中 `favorites._openid+qid` 和 `checkins._openid+date` 两条**唯一索引承担业务约束**，不能省：
> 它们让并发下的重复收藏/重复打卡直接失败，无需在代码里做查重。

> `records` 增长最快，建议每月导出到云存储归档，冷数据从主集合清理。

### 5.4 建库与导入（一个必踩的坑）

云开发控制台导入的 JSON **必须是 JSON Lines 格式**——每行一个完整对象、用换行分隔，
**不是**标准 JSON 数组，也不能缩进美化：

```
{"qid":10001,"module":"言语理解","stem":"..."}
{"qid":10002,"module":"数量关系","stem":"..."}
```

写成 `[{...},{...}]` 控制台会直接报「格式错误」，导入失败。
`scripts/import-questions.js` 已按此格式输出，`database/import/config.json` 同理。

完整建库步骤（建集合 → 设「仅管理端可读写」→ 建 16 条索引 → 导入题库）
见 `database/import/导入说明.md`。

## 6. 云函数设计

### 6.1 清单（10 个）

| 云函数 | 职责 | 关键设计 |
|---|---|---|
| `login` | 登录/注册、拉配置、同步资料 | 幂等；30 天内活跃用户不重复写库 |
| `question` | 抽题、查详情、搜索 | 抽题算法在云端，返回**不含 answer** |
| `answer` | **提交 + 云端判题** | 一次事务写 records / wrong_book / stats |
| `wrongbook` | 错题列表、移除、重做抽题 | 分页 20 条 |
| `favorite` | 收藏增删查 | 唯一索引兜底 |
| `checkin` | 打卡日历、提交打卡 | 连续天数计算在云端，时区按东八区 |
| `rank` | 周榜 / 邀请榜 | 读 `rank_week` 缓存，不实时聚合 |
| `share` | 生成带邀请参数的小程序码 | 调 `wxacode.getUnlimited`，`scene` 带 openid，按 md5 复用已生成文件 |
| `timer` | 定时触发器 | 每日 00:05 生成 daily_task；01:10 刷新榜单缓存；03:30 归档冷数据 |
| `track` | 埋点批量落库 | 单次最多 50 条，失败静默 |

### 6.2 抽题算法

```
输入：module, count=10, scene
1. scene=checkin  → 直接读 daily_task[今天].qids，所有人同一套题（公平 + 可缓存）
2. scene=practice：
   a. 取该用户近 7 天已作答 qid 集合（从 records 聚合，缓存 5 分钟）
   b. 候选池 = questions where module=? and status=1 and qid not in 已作答
   c. 按 difficulty 分桶，按用户历史正确率动态配比：
      正确率 > 80%  → 中档 70%、难题 30%
      正确率 40~80% → 简单 20%、中档 60%、难题 20%
      正确率 < 40%  → 简单 50%、中档 50%（保护信心）
   d. 各桶内随机取样后合并打乱
3. scene=review → 直接取 wrong_book 中 mastered=false 的 qid
4. 剥除 answer / analysis 后下发
```

**为什么剥除 answer**：客户端拿不到答案就无法本地判题，也就无法绕过 `answer` 云函数批量拖库。题库是这个产品唯一的资产，必须从源头保护。

**「即时解析」与「答案不下发」不冲突**——答案是用户**作答之后**才下发的，此时泄露已无意义：

| 模式 | 触发时机 | 请求次数 | 适用场景 |
|---|---|---|---|
| `instant`（默认） | 点选选项后立即提交该题，秒出解析 | 每组 10 次 | 专项练习、错题重做 |
| `batch` | 做完一组统一提交 | 每组 1 次 | 每日打卡、V1.1 模考 |

`answer` 云函数按 `items` 数组长度自动适配，两种模式共用一套判题逻辑。
instant 模式用路径语法只回填当前题的解析，其余题目 DOM 不动。

### 6.3 提交作答（一次事务完成 6 件事）

```js
// 客户端
await answer.submit({
  scene: 'practice',
  items: [{ qid: 10001, chosen: ['B'], costMs: 12000 }, ...]
})

// 云端单事务
// 1. 查 questions 判题
// 2. 批量写 records
// 3. upsert wrong_book（错 +1 / 对则 rightStreak+1）
// 4. 更新 users.stats（inc 原子操作）
// 5. 更新 questions.stat（难度校准数据源）
// 6. 返回 [{ qid, correct, answer, analysis }]
```

**事务边界（重要）**：20 题全量写入会产生 60+ 次操作，容易撞事务超时。
**只有错题本和用户统计进事务**；`records` 是只增日志、`questions.stat` 只用于难度校准，两者放事务外异步写，允许最终一致。

### 6.4 埋点设计（因日志只存 3 天而必须做）

标准版云函数日志仅保留 3 天，排查线上问题不能只靠它。
`track` 云函数把关键事件批量写进数据库，至少覆盖：

| 事件 | 关键字段 |
|---|---|
| `app_launch` | scene（场景值）、inviteBy |
| `practice_start` | module、count |
| `practice_submit` | correctCount、durationSec |
| `checkin` | streak |
| `poster_generate` | from（结果页/打卡页） |
| `share_click` | target（好友/朋友圈） |
| `error` | api、errMsg、基础库版本 |

## 7. 关键链路时序

### 7.1 冷启动（决定首屏时间）

```
app.onLaunch
  ├── wx.cloud.init()
  ├── 并行发起：login() + 读 storage 缓存
  │       └── 先渲染缓存 → 首页骨架屏 → 数据到达后静默刷新
  └── 检查 config.min_version（仅 release 环境校验，否则开发版会被自己的弹窗挡死）
```

**关键**：登录与首页数据请求必须**并行**，不能串行等待。

### 7.2 刷题闭环

```
首页/题库页 选择模块
  → question.draw(module, count=10)
  → 云端抽题（剥除 answer）→ 返回 10 题
  → 答题页逐题作答
       instant 模式：点选即提交单题 → 秒出解析 → 下一题
       batch 模式：做完 10 题 → 一次性提交 → 结果页
  → 结果页：得分、正确率、逐题解析、考点标签
  → 分享入口：生成战报海报
```

### 7.3 分享归因

```
用户 A 生成海报 → 云函数 share 调 wxacode.getUnlimited
  → scene 参数带 A 的 openid（≤32 字符，超长需换短 ID 映射表）
  → 新用户 B 扫码进入（场景值 1047 朋友圈 / 1007、1008 好友会话）
  → onLaunch 解析 scene → 写入 users.inviteBy = A
  → B 完成 10 题后，A 的邀请榜 +1
```

> `scene` 最大 32 个字符，openid 长度 28 位刚好放得下。
> 若后续要塞更多参数（如模块 ID），必须改为「短 ID + 映射表」，不能硬塞。

## 8. 性能设计

### 8.1 setData 优化（答题页是重灾区）

**反模式**：每题变动都 `setData({ questionList })` 全量刷新 10 题的 DOM。

**正确做法**：用路径语法只更新变化的字段。

```js
// 只更新第 3 题的选中态，其余 9 题 DOM 完全不动
this.setData({ [`list[${idx}].chosen`]: ['B'] })
```

配套规则：
- 题目数据挂 `this._questions`，**不参与渲染的数据绝不放进 `data`**
- 未渲染的题目图片延迟加载（`lazy-load` + 可视区判断）
- 解析面板默认折叠，展开时才 setData 解析内容

### 8.2 首屏优化

- 首页骨架屏 + `storage` 缓存上次数据（TTL 5 分钟），先渲染缓存再静默刷新
- 云函数**实例复用**（减少冷启动）：在云函数外层缓存 `db` 连接，不要每次请求新建
- 云函数内存建议配 **512MB**：内存与 CPU 配额正相关，能显著降低冷启动耗时

### 8.3 图片

- 题目配图走云存储，用 `wx.cloud.getTempFileURL` 换临时 HTTPS 链接，缓存 24 小时
- ⚠️ **云存储临时链接有效期 2 小时**，缓存必须早于过期时间刷新，否则出现图片裂图
- 格式优先 WebP，按需裁剪

### 8.4 离线兜底

刷题是移动场景，地铁/电梯常断网：

1. 作答写入本地队列（`storage`）
2. 监听 `wx.onNetworkStatusChange`，恢复后自动补交
3. 补交失败保留队列，下次启动重试（最多 3 次）

## 9. 增长设计

### 9.1 获客：战报海报裂变（主链路）

```
用户做完 10 题
  → 结果页展示「正确率 80%，击败全国 73% 的考友」
  → 点击「生成战报卡」
  → Canvas 2D 绘制海报（成绩 + 小程序码 + 打卡天数）
  → 保存到相册 / 分享到朋友圈
  → 新用户扫码进入 → 归因到邀请人
```

Canvas 2D 绘制要点：
- `wx.createSelectorQuery` 拿 canvas 节点，必须 `type: '2d'`
- 导出用 `canvasToTempFilePath`，`destWidth` 设为画布宽 × `pixelRatio`，否则模糊
- 海报上的小程序码走云函数 `wxacode.getUnlimited`，`scene` 带邀请人 openid

### 9.2 留存：打卡订阅消息

打卡**完成后**立即申请订阅（`wx.requestSubscribeMessage`）——此时用户意愿最高，授权率 40~60%，远高于冷启动弹窗的 5%。

模板：次日 8:00 推送「今日 10 道题已备好，昨日你击败了 XX% 的考友」。
每次授权可推送 1 次，需在 `users.subMsg.checkin` 记录剩余次数。

> ⚠️ 一次性订阅消息**不能用于营销**。文案必须是「服务完成通知」性质，且不能诱导分享，否则违规会被封禁模板。

### 9.3 排行榜（微信关系链已收紧，必须自建）

`wx.getFriendCloudStorage` / 群排行榜依赖的开放数据域在 2022 年后大幅限制，**非游戏类目基本拿不到好友数据**。

自建方案：
- 通过分享链接的 `scene` 绑定邀请关系（`users.inviteBy`）
- 「好友榜」退化为「我的邀请榜」——只展示我邀请的人
- 「全国榜」按周统计 `correctCount` 排序，存 `rank_week` 缓存集合，定时刷新

### 9.4 公众号联动（企业主体优势，V1.1 接）

- 公众号菜单 / 图文内嵌小程序卡片
- 文章底部「点击刷题」跳转，路径带 `utm` 做归因
- 长期稳定的免费流量入口

### 9.5 上线后 30 天重点指标

| 指标 | 健康值 | 说明 |
|---|---|---|
| 次日留存 | > 30% | 低于 25% 说明刷题体验有问题 |
| 人均日答题量 | > 15 题 | 低于 10 题说明题目质量或难度配比有问题 |
| 打卡完成率 | > 40% | 打卡用户是核心资产 |
| 分享率 | > 8% | 每张海报带来多少新用户，靠 `scene` 归因 |
| 分享转化率 | > 15% | 扫码打开 → 完成 10 题的比例 |

## 10. 合规与审核（最容易被卡的地方）

### 10.1 ICP 备案（第一关键路径，必须第 1 天启动）

2023 年 9 月起，所有小程序必须先完成 ICP 备案才能提交代码审核和发布。

完整流程与耗时：

| 环节 | 耗时 | 注意事项 |
|---|---|---|
| 微信平台初审 | 1~2 工作日 | 主体必须与微信认证主体**完全一致** |
| **工信部短信核验** | **24 小时内必须完成** | ⚠️ 收到 12381 短信后需登录工信部备案官网完成核验，**超时自动驳回，申请作废需重来** |
| 通管局终审 | 1~20 工作日（普遍 7~15） | 期间会电话核验，负责人手机务必畅通且如实回答 |
| **合计** | **首次主体 3~5 周；已有主体备案 2~3 周** | 无法人工加急，唯一提速方式是材料一次填对 |

备案信息中的「服务类目及服务内容描述」需详细准确，不能与所选类目相悖。

### 10.2 类目选择

| 选项 | 优劣 |
|---|---|
| **工具 > 效率**（推荐先选） | 门槛低、无需办学许可，提审通过率高 |
| 教育 > 在线教育 | 更贴合，但若涉及培训收费需办学许可；纯题库工具不需要 |

**策略**：先选工具类目快速上线，稳定后再追加教育类目。

### 10.3 用户隐私保护指引

- 微信后台填写《小程序用户隐私保护指引》
- 代码侧用 `wx.getPrivacySetting` 判断 + `<button open-type="agreePrivacyAuthorization">` 授权
- ⚠️ 该能力需基础库 **2.32.3+**，低版本必须做能力检测降级（见 §2.3）

### 10.4 头像昵称（接口已换代）

演进路径：`wx.getUserInfo`（废弃）→ `wx.getUserProfile`（**已回收**，2.27.1+ 只返回「微信用户」+ 灰色头像）→ **头像昵称填写能力**（当前唯一合规路径）。

必须用：
```html
<button open-type="chooseAvatar" bindchooseavatar="onChooseAvatar" />
<input type="nickname" />
```

> 备选：`<open-data>` 组件可免授权纯展示头像昵称，但**开发者拿不到数据值**，无法存库。本项目需要存库（排行榜展示），故走填写能力。

### 10.5 题库版权（教育类小程序被下架的头号原因）

- **不要直接搬运真题原文和官方解析**，全部自研或深度改编
- `questions.source` 标记来源，保留创作记录以备申诉
- 这是最高优先级的内容风险

### 10.6 提审技巧

`config.audit_mode = true` 时隐藏：排行榜、分享奖励、邀请入口。
审核通过后改回 `false`，**无需重新发版**。这个开关必须在 V1 就做进去，否则每次提审都要改代码重发。

其他红线：
- 不能用「分享后才能查看答案」这类强制分享，违反《微信小程序平台运营规范》
- 订阅消息不能滥用，不能诱导点击跳转
