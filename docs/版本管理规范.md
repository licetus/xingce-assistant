# 行测小助手 · 版本管理规范

> 小程序的版本管理比普通 App 复杂，因为它同时存在**三套互不同步的版本体系**。
> 理解这三者的边界，是避免上线事故的前提。

---

## 0. 三套版本体系（先分清这个）

| 体系 | 载体 | 更新方式 | 生效速度 | 需要审核 |
|---|---|---|---|---|
| **代码版本** | Git 仓库 | commit / tag | 即时（团队内） | 否 |
| **平台版本** | 微信后台 | 开发者工具上传 → 提审 → 发布 | **1~7 个工作日** | ✅ 是 |
| **业务版本** | 云数据库 `config` + 云函数 | 后台改配置 / 重传云函数 | **即时** | 否 |

**最要紧的一条**：小程序代码包**没有热更新**。改一个字都要重新提审。
所以凡是能用 `config` 配置或云函数解决的问题，**绝对不要写死在小程序代码里**。

这套架构里已经有三个为此预留的口子：

- `config.audit_mode` —— 提审时隐藏敏感入口，通过后关掉，不用重新发版
- `config.min_version` / `latest_version` —— 强制更新线，即时生效
- **云函数独立部署** —— 见 §6，这是最接近「热更」的能力

## 1. 微信平台版本体系

### 1.1 三个版本槽位

| 版本 | 谁能看到 | 数量 | 说明 |
|---|---|---|---|
| **开发版** | 仅开发者本人 | 每个开发者一份 | 开发者工具「上传」产生。**多人上传会互相覆盖** |
| **体验版** | 开发者 + 体验成员 | **全项目只有一份** | 从任一开发版「转体验版」，再次转换会覆盖 |
| **正式版** | 所有用户 | 一份（可灰度） | 提审通过后发布 |

### 1.2 必须知道的平台规则

- **体验版只有一份**。A 转了体验版，B 再转就会覆盖 A 的。多人协作要约定转换时机，建议在群里说一声
- **开发版和体验版共用同一个二维码**，靠微信里的「版本切换」按钮区分。发给同事前先确认他切到了哪
- **审核 1~7 个工作日**，实际常见 1~3 天。教育/工具类目如遇节假日会变慢，**排期时按 5 天算**
- **加急审核**有次数限制（与小程序信誉分挂钩），留给线上事故，日常不要用
- **分阶段发布（灰度）**：微信支持按比例逐步放量。V1.0 建议先用灰度观察崩溃率，再全量
- **版本回退**：只能回退到**上一个**线上版本，不能跳版本。回退后用户下次冷启动生效

### 1.3 回退能力对照表

| 出问题的是 | 最快止损手段 | 生效时间 |
|---|---|---|
| 小程序页面逻辑 Bug | 后台「版本回退」到上一版 | 用户下次冷启动（可能滞后） |
| 云函数逻辑 Bug | 云函数切回上一版本，或回滚代码重新部署 | **即时** |
| 运营文案 / 开关 / 强制更新线 | 改 `config` 集合 | **即时** |
| 题库数据错误 | `questions.status` 置 0 下架该批题 | **即时** |

> 看出规律了吗：**越往云端放，止损越快**。
> 这也是为什么判题、抽题这些核心逻辑全部放在云函数而不是客户端。

## 2. Git 分支策略

团队规模小、追求快速上线，用**极简三分支**，不要照搬 GitFlow（会拖慢节奏）。

```
main        线上正式版。受保护，只能从 develop / hotfix 合入
 └── develop   体验版。日常集成分支
      ├── feature/practice-instant   功能分支
      ├── feature/checkin-poster
      └── hotfix/judge-multi-answer  紧急修复
```

### 分支与平台版本的对应关系

| Git 分支 | 对应微信版本 | 谁负责上传 |
|---|---|---|
| `feature/*` | 开发版 | 开发者本人 |
| `develop` | **体验版** | 指定一人（避免互相覆盖） |
| `main` | **正式版**（提审） | 项目负责人 |

### 规则

1. `main` 设置分支保护，禁止直接 push
2. `feature/*` 从 `develop` 切，合回 `develop` 后删除
3. `hotfix/*` 从 `main` 切，修复后**同时合回 `main` 和 `develop`**（最容易忘的一步）
4. 打 tag 只在 `main` 上，且必须在提审**之前**

```bash
# 功能开发
git checkout develop
git pull
git checkout -b feature/xxx
# ... 开发 ...
git checkout develop
git merge --no-ff feature/xxx
git branch -d feature/xxx

# 发版
git checkout main
git merge --no-ff develop
git tag -a v1.0.0 -m "V1.0.0 首个正式版"
git push origin main --tags
```

### 当前仓库状态

```
* develop    ← 当前所在
  main
613171f  feat(update): 建立版本管理体系与更新机制
ed91b55  chore: 初始化行测小助手工程骨架
```

84 个文件已入库。`.gitignore` 已处理微信特有的坑，其中最关键的两条：

- **`project.private.config.json`** —— 开发者工具会自动往里写个人配置，不忽略的话团队天天解冲突
- **`miniprogram/config.js`** —— 存放真实云环境 ID，模板 `config.example.js` 入库，实际配置不入库

## 2.5 远端仓库（GitHub）

### 初始化

在 GitHub 网页创建**空**仓库（**不要**勾 README / .gitignore / LICENSE，会和本地历史冲突导致推送被拒），然后：

```bash
./scripts/setup-github.sh https://github.com/<用户名>/<仓库名>.git
```

脚本会加远端、推 `main` 和 `develop`，不做强推也不改历史。

### 推送后必须在网页上做的配置

| 配置项 | 位置 | 说明 |
|---|---|---|
| 默认分支改为 `develop` | Settings → General → Default branch | 日常开发在 develop，PR 默认往 develop 合 |
| 保护 `main` | Settings → Branches → Add ruleset | 勾 Require a pull request before merging |
| 邀请协作者 | Settings → Collaborators | 小程序后台也要同步加开发者/体验成员 |

### 敏感配置分离

`miniprogram/config.js` 存放真实云环境 ID，**已在 `.gitignore` 中，永不入库**。
模板 `config.example.js` 入库，`app.js` 在 config.js 缺失时回退读取模板的占位值并告警，
保证克隆下来能打开不白屏。

新成员上手：

```bash
cp miniprogram/config.example.js miniprogram/config.js
# 编辑 config.js 填入自己的云环境 ID（开发/测试/生产可以各用各的）
```

`project.config.json` 里的 `appid` 同理。若团队中不同人用不同 AppID 测试，
把 appid 写进 `project.private.config.json`（该文件优先级更高且已忽略），
`project.config.json` 保持占位值即可。

### 公开仓库的三条红线

本仓库设为 Public，推送前逐条确认：

1. **不提交真实 AppID / 云环境 ID** —— 靠上面那套 config 分离机制保证
2. **不提交题库正文** —— 题库走 `scripts/import-questions.js` 导入到云数据库，不进 Git。
   `scripts/sample-questions.csv` 只是 6 道示例题，用于验证脚本
3. **不提交任何密钥** —— 云开发模式下不需要配 API Secret，如果将来接入第三方服务，
   密钥一律放云函数环境变量或云开发配置，绝不写进代码

> 已知会公开的内容：`docs/架构设计.md`（完整技术架构）、`docs/版本管理规范.md`、
> 全部业务代码。如果这些属于不希望对外披露的信息，把仓库改成 Private 即可，
> 免费账号不限私有仓库数量。

## 3. 版本号规范

采用 SemVer `MAJOR.MINOR.PATCH`，与 Git tag 保持一致：

| 段 | 何时 +1 | 例子 |
|---|---|---|
| `MAJOR` | 不兼容变更：云函数接口改契约、数据库结构破坏性调整 | `2.0.0` |
| `MINOR` | 新增功能，向下兼容 | `1.1.0` |
| `PATCH` | Bug 修复、文案调整 | `1.0.1` |

**微信后台填写的版本号要和 Git tag 完全一致**。这个版本号只是展示用，
微信不做任何校验，但出事故排查时它就是唯一线索，必须能对上。

版本号在开发者工具「上传」时填写，会显示在小程序资料页。

## 4. 提交信息规范

用 Conventional Commits，好处是可以自动生成 CHANGELOG：

```
<type>(<scope>): <subject>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `perf` | 性能优化（如 setData 优化、包体积优化） |
| `refactor` | 重构，不改功能 |
| `docs` | 文档 |
| `chore` | 构建/配置/依赖 |

示例：

```
feat(practice): 支持逐题提交实现即时解析
fix(answer): 修正多选题答案顺序敏感导致误判
perf(question-card): 选中态下沉到组件内减少 setData 体积
chore(ci): 云函数改为云端安装依赖
```

## 5. 发布流程

### 5.1 提审前检查清单

**代码层**
- [ ] 主包体积 < 1.5MB（开发者工具「代码依赖分析」查看）
- [ ] `app.json` 里所有页面路径真实存在，无残留的空页面
- [ ] 云函数全部已部署到**生产环境**，且选了「云端安装依赖」
- [ ] 数据库索引已建齐（对照 `database/indexes.md` 的 16 条）
- [ ] 所有集合安全规则 = 「仅管理端可读写」

**合规层**
- [ ] `config.audit_mode = true`（隐藏排行榜/邀请/奖励）
- [ ] 《用户隐私保护指引》已配置且可正常打开
- [ ] 头像昵称用的是 `chooseAvatar` + `nickname` 组件，不是废弃的 `getUserProfile`
- [ ] 题库 `source` 字段如实标注，无搬运真题原文
- [ ] 无强制分享才能看答案这类违规设计

**功能层**
- [ ] 真机跑通主链路：刷题 → 解析 → 错题本 → 打卡 → 分享海报
- [ ] 断网场景：作答能保存，联网后自动补交
- [ ] 首次进入、未登录、题库为空三种边界状态都不白屏

**提审材料**
- [ ] 测试账号（如需要登录的页面）
- [ ] 录屏演示（教育类目建议提供，能显著减少驳回）
- [ ] 版本说明填清楚这次改了什么

### 5.2 发布节奏建议

```
Day 1  main 打 tag → 上传体验版 → 内部验收
Day 2  转体验版 → 体验成员测 1 天
Day 3  提交审核（打开 audit_mode）
Day 4-7  等待审核，期间只改云函数和 config，不改小程序代码
Day 8  审核通过 → 灰度 10% → 观察崩溃率 2 小时
Day 8  全量 → 关闭 audit_mode
```

**审核期间不要动小程序代码** —— 改了就得重新提审，白等。
这段时间的窗口正好用来改云函数和 config，那些不需要审核。

## 6. 云函数：变相的热更新能力

这是小程序架构里最容易被忽略的一张牌。

**云函数独立于小程序代码部署，不需要提审。**

**这意味着**：判题逻辑算错了、抽题算法要调优、排行榜统计口径错了 ——
改云函数、重新部署，**几分钟生效，不用等审核**。

### 6.1 代码存储模型（重要）

```
本地 Git 仓库                    云开发云端
─────────────                   ─────────────
完整提交历史          ──部署──▶   $LATEST   每次部署覆盖，无历史
分支 / diff / 回滚              版本 1     显式发布的快照，代码锁定
唯一真相                        版本 2     显式发布的快照，代码锁定
```

**云端不是版本管理系统**：没有 commit、没有分支、没有 diff。
每次部署都是整体覆盖 `$LATEST`，历史只保留你**显式发布**的版本快照。

所以：代码丢了能从云端拉回 `$LATEST`（`tcb fn code download`），
但拉不回上周的某个中间状态 —— **Git 才是唯一真相，云端只是运行副本。**

### 6.2 部署的四条路径

| 方式 | 命令 / 操作 | 适合场景 |
|---|---|---|
| **CLI（推荐）** | `tcb fn deploy --all` | 批量部署，可脚本化、可进 CI |
| 开发者工具 | 右键函数目录 → 上传并部署 | 临时改一个函数 |
| 控制台在线编辑 | 云开发控制台 → 云函数 | 紧急小改，但不留本地副本，**不建议** |
| 云托管 Git 集成 | 绑定 GitHub，push 触发构建 | 仅适用于云托管容器服务（见 6.4） |

CLI 用法（已配好 `cloudbaserc.json`）：

```bash
npm i -g @cloudbase/cli
tcb login                          # 浏览器授权

export CLOUD_ENV_ID=你的环境ID
./scripts/deploy-functions.sh      # 部署全部，含语法前置检查
./scripts/deploy-functions.sh answer   # 只部署 answer
```

`cloudbaserc.json` 里 `envId` 故意留占位值，部署时用 `--env-id` 参数覆盖，
这样真实环境 ID 不会进 Git（仓库是 Public）。

### 6.3 版本与灰度

版本 = 云函数在某一时刻的**快照**，包含代码 + 配置（超时、内存、环境变量）。

关键规则：

- 云函数**始终存在 `$LATEST`**，部署代码改的就是它
- 发布版本 = 从 `$LATEST` 当前状态打快照，**发布后代码与配置锁定，不可修改**
- **流量只能在两个版本之间分配**，比例总和必须等于 100%
- **同一用户固定路由**：带 openid 的请求，该用户的所有请求会一直打到同一版本
  （这点很关键，否则用户会在新旧逻辑之间反复横跳，体验割裂）

正确流程：

```
1. 发布版本 1（保存当前稳定代码）
2. 版本 1 流量 100%，$LATEST 流量 0%
3. 部署新代码（改的是 $LATEST）
4. $LATEST 设 10%，版本 1 设 90% → 观察日志
5. 没问题就逐步加到 100%；出问题把 $LATEST 调回 0% 立即回滚
```

> ⚠️ 网上有些文章说「云开发不支持灰度，要上传 `myFunction_v2` 再在客户端手动路由」——
> 那是过时或错误的说法。原生灰度能力从微信开发者工具 1.02.2005112 起就支持了，
> 不需要自己造轮子。

### 6.4 云托管（CloudRun）是不同的东西

云托管是**容器服务**，和云函数不是一回事：

| | 云函数 | 云托管 |
|---|---|---|
| 形态 | 单个函数 | 容器（需 Dockerfile） |
| 语言 | Node / Python / PHP 等 | 任意语言框架 |
| Git 集成 | ❌ 无 | ✅ 支持 GitHub/GitLab/Gitee，Webhook 自动构建 |
| 看控制台 | 微信开发者工具云开发控制台 | 独立的微信云托管控制台 |
| 本项��� | ✅ 用的就是这个 | 暂不需要 |

云托管是**唯一支持 Git 驱动自动部署**的一块，但它需要容器化，
对当前这个规模的项目是过度设计。等后续有独立的后端服务了再考虑。

### 代价：必须向前兼容

小程序用户不会同时升级（微信异步推送，可能滞后好几版）。
所以同一时刻线上会有多个小程序版本在跑，它们调的是同一批云函数。

**云函数接口只能加字段，不能删字段、不能改语义。**

```js
// ❌ 破坏性变更：老版本小程序读不到 answer 字段，直接崩
{ qid, correct, analysis }

// ✅ 向前兼容：新增字段，老字段保留，等所有用户都升级后再废弃（至少留 2 个版本周期）
{ qid, correct, analysis, answer, explanationRich }
```

**规则**：
1. 改云函数前先问：老版本小程序调这个接口会怎样？
2. 要删字段，先保留 2 个版本周期，确认 `latest_version` 已推进再删
3. 数据库加字段同理 —— 老代码不认识新字段，但新代码要能容忍老数据缺字段

## 7. 强制更新机制

代码已实现，见 `miniprogram/utils/update.js`，在 `app.js` 启动时调用。

### 三级策略

| 触发条件 | 行为 | 用户能否忽略 |
|---|---|---|
| `current < min_version` | 弹窗阻断，一键重启 | ❌ 不能 |
| `current < latest_version` | 提示一次，每天最多一次 | ✅ 能 |
| 微信推送了新包 | 提示重启（`onUpdateReady`） | ✅ 能 |

### 用法

在 `config` 集合里改这两个字段即可，不用发版：

```js
{ key: 'latest_version', value: '1.1.0' }   // 柔性提示
{ key: 'min_version',    value: '1.0.0' }   // 强制更新线
{ key: 'update_note',    value: '修复了多选题判分问题，请更新' }
```

### 两个必须注意的实现细节

**1. 只在正式版校验。**
开发版和体验版 `wx.getAccountInfoSync()` 返回的 `version` 是空字符串，
不排除的话本地调试会被自己的强制更新弹窗挡死。

```js
if (envVersion !== 'release') return;
```

**2. 强制更新弹窗要延后触发。**
抢在首页渲染前弹出会被页面覆盖，出现「白屏后弹窗」的诡异现象。
`app.js` 里延后 800ms 调用。

### 一个现实约束

小程序**没有任何 API 能真正锁死用户界面**。不可取消的弹窗已经是最强手段。
如果新包还没推到该用户（微信异步推送滞后），只能引导他删除小程序重新搜索 ——
这也是 `utils/update.js` 里那个兜底弹窗存在的原因。

## 8. 常见坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 提交了 `project.private.config.json` | 团队天天解冲突 | 已在 `.gitignore` 忽略 |
| 多人抢着转体验版 | 互相覆盖，测试结论混乱 | 指定一个人负责转换 |
| 审核期间改小程序代码 | 前功尽弃，重新排队 | 这段时间只改云函数和 config |
| 云函数删字段 | 老版本小程序崩溃 | 只加不删，废弃留 2 个版本周期 |
| 忘了给云函数装依赖 | 生产环境报错找不到模块 | 上传时选「云端安装依赖」 |
| 版本号和 tag 对不上 | 出事故排查时找不到对应代码 | 提审前先打 tag，再上传 |
| hotfix 只合了 main | develop 上 Bug 复活 | hotfix 必须同时合回 develop |

## 9. 一页速查

```bash
# 日常开发
git checkout develop && git pull
git checkout -b feature/xxx
```
