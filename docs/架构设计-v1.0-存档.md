# 行测小助手 · 微信小程序架构设计

> 版本 v1.0 ｜ 目标：**4 周内提审上线**，首月以「刷题留存 + 分享裂变」双轮获取种子用户
> 技术栈：原生小程序 + 微信云开发 ｜ 主体：企业/个体工商户 ｜ 题库：自有自研

---

## 0. 一页纸结论

| 决策项 | 结论 | 为什么 |
|---|---|---|
| 开发框架 | **原生小程序**（不用 Taro/uni-app） | V1 只发微信一端，跨端框架带来 15~20% 性能损耗和调试成本，换不来收益 |
| 后端 | **微信云开发 CloudBase** | 免服务器、免域名白名单、免 SSL 证书、免备案后端，登录鉴权开箱即用。上线周期压缩 2~3 周 |
| UI 组件库 | **手写轻量组件**，不引入 TDesign 全量 | TDesign 全量约 300KB+，会吃掉主包 2MB 预算的 15%。刷题类 UI 简单，自研 8 个组件足够 |
| 数据访问 | **全部走云函数**，数据库安全规则设为「仅管理端」 | 题库是核心资产。客户端直连数据库可被批量拖库 |
| 判题位置 | **云端判题** | 下发的题目不含 `answer` 字段，从源头杜绝题库泄露 |
| 状态管理 | `globalData` + 自研 50 行事件总线 | mobx-miniprogram 增加约 30KB，V1 规模用不上 |

## 1. 技术选型

### 1.1 为什么是云开发（关键决策）

传统自建后端要跑完这条链：**买服务器 → 买域名 → ICP 备案 → 申请 SSL 证书 → 配置 HTTPS → 微信后台配 request 合法域名 → 后端实现登录态**。
云开发把这条链全部砍掉，只剩「开通环境」一步。

| 能力 | 云开发方案 |
|---|---|
| 用户鉴权 | `cloud.getWXContext()` 直接拿 openid，无需 `wx.login` + code2session |
| 数据库 | 云数据库（文档型，MongoDB 语法），控制台建索引 |
| 文件存储 | 云存储，自带 CDN，可用 `wx.cloud.getTempFileURL` 换 HTTPS 链接 |
| 定时任务 | 定时触发器（Cron），用于每日生成任务、刷新榜单缓存 |
| 服务端逻辑 | 云函数（Node.js 16/18） |

> ⚠️ 云开发的边界要提前认清：单云函数最多 100 并发实例、单次执行超时 60s（可调至 60s 上限）、单次返回包体 ≤ 6MB（云调用）。
> 日活 5 万以内的刷题类小程序完全够用。等 DAU 到这个量级再迁自建，数据可通过云开发导出平滑迁移。

### 1.2 依赖清单

```
运行时依赖：零（不装任何 npm 包进主包）
            —— 这是刻意设计，主包体积全部留给业务代码和图标

开发工具：微信开发者工具（最新稳定版）
基础库最低版本：2.25.0   （覆盖约 98% 微信用户，支持 Canvas 2D、skyline 可选）
```

## 2. 分包规划

微信小程序硬限制：**单个分包/主包 ≤ 2MB，总大小 ≤ 20MB**。
主包控制在 **1.2MB 以内**是安全线（给图标、字体、后续迭代留余量）。

### 2.2 为什么错题本列表放主包

`tabBar.list[].pagePath` **必须指向主包页面**（不能是分包路径）。四个 tab（首页/练习/错题/我的）因此都得在主包。
错题列表页本身很轻（列表 + 复用 `question-card`），代价约 30KB，换取的是底部导航的完整体验，值得。

### 2.3 预下载规则

```json
"preloadRule": {
  "pages/index/index": { "network": "all", "packages": ["pkg-rank"] },
  "pages/mine/mine":   { "network": "wifi", "packages": ["pkg-rank"] }
}
```

首页是最大流量入口，进首页就静默预下载打卡分包，用户点「每日打卡」时零等待。

## 3. 数据模型

云开发数据库是文档型。**所有集合安全规则设为「仅管理端可读写」**，客户端一律通过云函数访问。

### 3.1 集合清单

| 集合 | 用途 | 预估量级（1 万 DAU / 半年） |
|---|---|---|
| `users` | 用户主档、统计、打卡状态 | 30 万 |
| `questions` | 题库 | 5 千 ~ 2 万（固定） |
| `qgroups` | 材料题共用材料（资料分析/言语理解） | 1 千 |
| `records` | 答题流水 | 3000 万 ⚠️ 最大集合 |
| `wrong_book` | 错题本（冗余表，避免聚合 records） | 300 万 |
| `favorites` | 收藏 | 50 万 |
| `checkins` | 每日打卡 | 500 万 |
| `daily_task` | 每日任务（预生成题目集） | 365 |
| `config` | 运营配置 / 审核开关 | 20 |
| `rank_week` | 周榜缓存（定时刷新） | 1 万 |

### 3.2 核心 Schema

**questions** — 题库（核心资产）
```js
{
  qid: 10001,                  // 业务主键，Number，唯一索引
  module: '资料分析',           // 常识判断|言语理解|数量关系|判断推理|资料分析
  subtype: '增长率计算',        // 二级考点
  type: 'single',              // single | multi | material
  stem: '题干文本',
  options: [{ key: 'A', text: '选项内容' }],
  answer: ['B'],               // 数组，兼容多选
  analysis: '解析文本',
  difficulty: 3,               // 1-5
  tags: ['增长率', '基期量'],
  materialId: null,            // type=material 时指向 qgroups.gid
  images: [],                  // 云存储 fileID
  source: 'self',              // 自研标记，版权合规用
  status: 1,                   // 1 上架 / 0 下架
  stat: { done: 0, correct: 0 }, // 全局作答统计，用于难度校准
  createdAt: Date
}
```

**users** — 用户主档
```js
{
  _openid: 'oXXXX',            // 唯一索引
  profile: { nickName: '', avatarUrl: '', grade: '省考' },
  inviteBy: null,              // 邀请人 _openid，自建好友关系
  checkin: { streak: 0, maxStreak: 0, lastDate: '', totalDays: 0 },
  stats: {
    totalDone: 0, totalCorrect: 0,
    byModule: {                // 定长 5 键，方便前端直接渲染
      '常识判断': { done: 0, correct: 0 },
      '言语理解': { done: 0, correct: 0 },
      '数量关系': { done: 0, correct: 0 },
      '判断推理': { done: 0, correct: 0 },
      '资料分析': { done: 0, correct: 0 }
    }
  },
  subMsg: { checkin: 0 },      // 订阅消息剩余可推送次数
  createdAt: Date, lastActiveAt: Date
}
```

**records** — 答题流水（只写不读，用于离线分析）
```js
{ _openid, qid, module, chosen: ['B'], correct: true, costMs: 12000,
  scene: 'practice',   // practice|review|checkin|exam
  date: '2026-08-29',  // 冗余日期，便于按天聚合
  createdAt: Date }
```

**wrong_book** — 错题本
```js
{ _openid, qid, wrongCount: 2, rightStreak: 0, mastered: false,
  lastWrongAt: Date, createdAt: Date }
```
> 移除规则：连续答对 2 次（`rightStreak >= 2`）自动置 `mastered: true`。这是艾宾浩斯记忆曲线的最简实现。

**checkins**
```js
{ _openid, date: '2026-08-29', doneCount: 10, correctCount: 7,
  durationSec: 320, createdAt: Date }
```

**config** — 运营配置（**提审救命用**）
```js
{ key: 'audit_mode', value: false }     // 审核模式：隐藏分享诱导、排行榜等敏感入口
{ key: 'share_text', value: '...' }     // 分享文案，可热更
{ key: 'min_version', value: '1.0.0' }  // 强制更新
{ key: 'home_banner', value: {...} }
```

### 3.3 索引（必须建，否则量上来就慢）

| 集合 | 索引 | 类型 |
|---|---|---|
| `questions` | `qid` | 唯一 |
| `questions` | `module + status + difficulty` | 非唯一 |
| `questions` | `subtype + status` | 非唯一 |
| `users` | `_openid` | 唯一 |
| `users` | `stats.totalDone`（倒序） | 非唯一 |
| `records` | `_openid + createdAt`（倒序） | 非唯一 |
| `records` | `_openid + qid` | 非唯一 |
| `wrong_book` | `_openid + mastered + lastWrongAt`（倒序） | 非唯一 |
| `favorites` | `_openid + qid` | **唯一**（防重复收藏） |
| `checkins` | `_openid + date` | **唯一**（防重复打卡） |
| `checkins` | `date + correctCount`（倒序） | 非唯一（排行榜用） |

> 云开发数据库单次 `limit` 上限 1000，批量插入建议每批 500 条。
> `records` 增长快，建议每月导出到 COS 归档，冷数据从主集合清理。

## 4. 云函数设计

### 4.1 清单

| 云函数 | 职责 | 关键设计 |
|---|---|---|
| `login` | 登录/注册、拉配置、同步资料 | 幂等，30 天内活跃用户不重复写库 |
| `question` | 抽题、查详情、搜索 | 抽题算法在云端，返回**不含 answer** |
| `answer` | **批量提交 + 云端判题** | 单次接收 10~20 题作答，一次事务写 records/wrong_book/stats |
| `wrongbook` | 错题列表、移除、重做抽题 | 分页 20 条 |
| `favorite` | 收藏增删查 | 唯一索引兜底 |
| `checkin` | 打卡日历、提交打卡 | 连续天数计算在云端（时区按东八区） |
| `rank` | 周榜/总榜 | 读 `rank_week` 缓存，不实时聚合 |
| `share` | 生成带邀请参数的小程序码 | 调 `wxacode.getUnlimited`，`scene` 带 openid，按 md5 复用已生成文件 |
| `timer` | 定时触发器 | 每日 00:05 生成 daily_task、01:10 刷新榜单缓存、03:30 归档冷数据 |
| `track` | 埋点批量落库 | 单次最多 50 条，失败静默 |

### 4.2 抽题算法（V1 版本）

```
输入：module, count=10, scene
1. 若 scene=checkin → 直接读 daily_task[今天].qids，所有人同一套题（公平 + 可缓存）
2. 若 scene=practice：
   a. 取出该用户近 7 天已作答 qid 集合（从 records 聚合，缓存 5 分钟）
   b. 候选池 = questions where module=? and status=1 and qid not in 已作答
   c. 按 difficulty 分桶，按用户历史正确率动态配比：
      正确率 > 80% → 中档题 70%、难题 30%
      正确率 40~80% → 简单 20%、中档 60%、难题 20%
      正确率 < 40% → 简单 50%、中档 50%（保护信心）
   d. 各桶内随机取样后合并打乱
3. 剥除 answer / analysis 后下发
```

**为什么剥除 answer**：客户端拿不到答案，就无法本地判题，也就无法绕过 `answer` 云函数直接拖库。

**但「即时解析」照样能做**——两者不冲突。答案是在用户**作答之后**才下发的，此时泄露已无意义：

| 模式 | 触发时机 | 请求次数 | 适用场景 |
|---|---|---|---|
| `instant`（默认） | 点选选项后立即提交该题，秒出解析 | 每组 10 次 | 专项练习、错题重做 |
| `batch` | 做完一组统一提交，中途不看解析 | 每组 1 次 | 每日打卡、限时模考 |

`answer` 云函数按 `items` 数组长度自动适配，两种模式共用一套判题逻辑。
instant 模式下用路径语法只回填当前题的解析（`setData({['list[n].result']: r})`），其余题目 DOM 不动。

### 4.3 提交作答（一次事务，减少网络往返）

```js
// 客户端：做完 10 题后一次性提交
await answer.submit({
  scene: 'practice',
  items: [{ qid: 10001, chosen: ['B'], costMs: 12000 }, ...]
})

// 云端：单事务完成 6 件事
// 1. 查 questions 判题
// 2. 批量写 records
// 3. upsert wrong_book（错 +1 / 对则 rightStreak+1）
// 4. 更新 users.stats（inc 原子操作）
// 5. 更新 questions.stat（难度校准数据源）
// 6. 返回 [{qid, correct, answer, analysis}]
```

用 `db.runTransaction` 保证一致性。一次网络往返完成 6 件事，比 6 次请求快一个数量级。

## 5. 性能设计

### 5.1 setData 优化（刷题页是重灾区）

**反模式**：每题变动都 `setData({ questionList })` 全量刷新 10 题的 DOM。

**正确做法**：用路径语法只更新变化的字段。

```js
// 只更新第 3 题的选中态，其余 9 题 DOM 完全不动
this.setData({ [`list[${idx}].chosen`]: ['B'] })
```

配套规则：
- 题目数据放 `this.data` 之外（挂 `this._questions`），不参与渲染的数据绝不放进 data
- 未渲染的题目图片延迟加载（`lazy-load` + 可视区判断）
- 解析面板默认折叠，展开时才 setData 解析内容

### 5.2 首屏优化

- 首页骨架屏 + `storage` 缓存上次数据（TTL 5 分钟），先渲染缓存再静默刷新
- `app.js` 里登录与首页数据请求**并行**，不串行等待
- 云函数开启**固定出口 IP** 无必要；但开启**实例复用**（减少冷启动）很关键：在云函数外层缓存 db 连接

### 5.3 图片

题目配图统一走云存储，通过 `wx.cloud.getTempFileURL` 换临时 HTTPS 链接，并在 `cache.js` 缓存 24 小时（云存储临时链接有效期 2 小时，注意过期刷新）。格式优先 WebP + 按需裁剪。

### 5.4 离线兜底

刷题是移动场景，地铁/电梯里常断网。网络异常时：
1. 作答写入本地队列（`storage`）
2. 监听 `wx.onNetworkStatusChange`，恢复后自动补交
3. 补交失败保留队列，下次启动重试（最多 3 次）

## 6. 增长设计（快速获客）

### 6.1 分享裂变主链路

```
用户做完 10 题
   → 结果页展示「正确率 80%，击败全国 73% 的考友」
   → 点击「生成战报卡」
   → Canvas 2D 绘制海报（成绩 + 小程序码 + 打卡天数）
   → 保存到相册 / 分享到朋友圈
   → 新用户扫码进入 → 场景值 1047（朋友圈）或 1007/1008（好友会话）
```

海报是关键。Canvas 2D 绘制要点：
- 用 `wx.createSelectorQuery` 拿 canvas 节点，必须 `type: '2d'`
- 小程序码通过云函数调 `wxacode.getUnlimited`，传 `scene` 带上邀请人 openid
- 导出图片用 `canvasToTempFilePath`，`destWidth` 设为画布宽 × `pixelRatio`，否则模糊

### 6.2 打卡订阅消息

打卡完成后立即申请订阅（`wx.requestSubscribeMessage`）——此时用户意愿最高，授权率能到 40~60%，远高于冷启动弹窗的 5%。

模板：次日 8:00 推送「今日 10 道题已备好，昨日你击败了 XX% 的考友」。
每次授权可推送 1 次，需在 `users.subMsg.checkin` 记录剩余次数，累计推送。

**注意**：一次性订阅消息不能用于营销。文案必须是「服务完成通知」性质，且不能诱导分享，否则违规会被封禁模板。

### 6.3 排行榜

⚠️ **微信关系链能力已收紧**：`wx.getFriendCloudStorage` / 群排行榜依赖的开放数据域在 2022 年后大幅限制，非游戏类目基本拿不到好友数据。

**采用自建方案**：
- 通过分享链接的 `scene` 参数绑定邀请关系（`users.inviteBy`）
- 「好友榜」退化为「我的邀请好友榜」——展示我邀请的人的排名
- 「全国榜」按周统计 `correctCount` 排序，存 `rank_week` 缓存集合，定时刷新

### 6.4 公众号联动（企业主体优势）

企业主体可绑定公众号：
- 公众号菜单 / 图文内嵌入小程序卡片
- 文章底部「点击刷题」跳转，路径带 `utm` 参数做归因
- 这是长期稳定的免费流量入口，V1.1 就该接

## 7. 合规与审核（最容易被卡的地方）

### 7.1 上线前置清单

| 项 | 说明 | 状态 |
|---|---|---|
| **ICP 备案** | 2024 年起小程序上架必须完成备案，企业主体约 3~20 个工作日。**这是最长的关键路径，必须第一天启动** | ⬜ |

| 用户协议 | 服务端可配置，小程序内可访问 | ⬜ |

### 7.2 代码侧合规要点

- **头像昵称**：`wx.getUserProfile` 已废弃。必须用
  `<button open-type="chooseAvatar">` + `<input type="nickname">`
- **题库版权**：`questions.source` 标记来源，**不要直接搬运真题原文和官方解析**。
  自研或深度改编。这是教育类小程序被投诉下架的头号原因
- **分享**：不能用「分享后才能查看答案」这类强制分享，违反《微信小程序平台运营规范》
- **订阅消息**：不能滥用，不能诱导点击跳转
- **内容安全**：V1 无 UGC。V2 若开放用户上传题目，必须接 `msgSecCheck` / `imgSecCheck`

### 7.3 提审技巧

`config.audit_mode = true` 时隐藏：排行榜、分享奖励、邀请入口。
审核通过后改回 `false`，无需重新发版。这个开关一定要在 V1 就做进去，否则每次提审都要改代码重发。

| 周期 | 交付 | 并行事项 |
|---|---|---|
| **W1** | 工程骨架、云开发环境、数据模型与索引、题库导入脚本 | 🔴 第 1 天提交 **ICP 备案**（耗时最长）、注册小程序、选类目 |

### 上线后 30 天重点看这几个数

| 指标 | 健康值 | 说明 |
|---|---|---|
| 次日留存 | > 30% | 低于 25% 说明刷题体验有问题 |
| 人均日答题量 | > 15 题 | 低于 10 题说明题目质量或难度配比有问题 |
| 打卡完成率 | > 40% | 打卡用户是核心资产 |
| 分享率 | > 8% | 每张海报带来多少新用户，靠 `scene` 归因 |
| 分享转化率 | > 15% | 扫码打开 → 完成 10 题的比例 |
